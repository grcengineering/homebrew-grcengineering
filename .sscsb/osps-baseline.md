# OSPS Baseline assessment — grcengineering/homebrew-grcengineering

The [OpenSSF Project Security Baseline](https://baseline.openssf.org/) is a set of
minimum, maturity-tiered security requirements. sscsb maps the controls it installs
to the Baseline's requirement families so you can see, and attest to, which the repo
already satisfies. Run `sscsb report` for the live, machine-readable version (the
OSPS column) and `sscsb report --format json` for evidence.

## Coverage by requirement family

| OSPS family | Intent | Covered by sscsb controls |
|---|---|---|
| **OSPS-AC** Access Control | protect the primary branch; least-privilege access | `branch-protection`, `commit-signing`, `gittuf` |
| **OSPS-BR** Build & Release | integrity/provenance of source and released assets | `sigstore-signing`, `slsa-provenance`, `github-attestations`, `sbom-attestation`, `provenance-verify`, `model-signing`, `actions-audit` |
| **OSPS-QA** Quality | dependency transparency, review, well-documented code | `sbom`, `renovate`, `package-trust`, `sast` |
| **OSPS-SA** Security Assessment | architecture/security documentation | `security-insights`, `scorecard` |
| **OSPS-VM** Vulnerability Management | reporting process + finding/fixing defects | `vuln-scan`, `codeql`, `fuzzing`, `openvex`, `security-insights` |
| **OSPS-DO** Documentation | user & security docs | `SECURITY.md` (installed), `security-insights` |
| **OSPS-LE** Legal | license present, DCO/CLA | `LICENSE` (confirm) |
| **OSPS-GV** Governance | roles, decision-making | maintainer-authored (`security-insights` roles) |

## What this table is, and is not, for this repository

The table above is sscsb's generic control-to-family mapping: it says which sscsb
control WOULD cover each family, not which are enabled here. Several named controls
are deliberately off in this tap because it has no build, no releases and no package
dependencies of its own — `sbom`, `vuln-scan`, `renovate`, `package-trust`,
`sigstore-signing`, `slsa-provenance`, `github-attestations`, `sbom-attestation`,
`fuzzing`, `openvex`, `model-signing`, `gittuf`. `sscsb status` is the live answer;
`.sscsb/config.toml` carries the reason beside each toggle.

What covers **OSPS-BR** here is not an attestation this repo produces but one it
CHECKS: `formula-integrity.yml` verifies upstream's Sigstore bundle or SLSA
provenance for every artifact a formula points at, pinned to the expected source
repository and tag, on every pull request, every push to `main`, and weekly against
already-merged formulae. For a distribution channel that is the load-bearing
Build & Release control; signing the tap's own Ruby files would attest nothing a
user consumes.

## Maturity note

sscsb's controls target the Baseline's **Level 1–2** technical requirements (the
machine-enforceable ones). Level-3 and the Documentation/Legal/Governance families
include human attestations sscsb cannot auto-satisfy — fill those in your
`security-insights.yml` and project docs.
